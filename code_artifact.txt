任务一：打通 `/api/v1/**` 前后端代理、Context-Path 与鉴权拦截链路（最高优先级）

【问题描述】

【请 Cursor 按以下步骤核查并修复】
1. 检查后端上下文路径（Context-Path）：

2. 检查后端鉴权与路由拦截器：
   - 查看 `backend/disaster-survey-admin/src/main/java/com/santech/server/filter/WebMvcConfig.java` 与 `SysInterceptor.java`。
   - 核对以下两点：
     a) `/api/v1/**` 是否在拦截器的 Token 校验范围内（确保已登录用户携带有效 Token 可正常访问，未登录用户被正常拦截）。
     b) 如果 `SysInterceptor` 存在基于数据库权限表（如 `JC_ACTION`）的精细 URL 鉴权或硬编码的旧路径前缀判断，请确认 `/api/v1/**` 不会因为未录入旧权限表而直接返回 403/无权限。
     c) 修复方案：在 `SysInterceptor` 中对已通过登录 Token 校验的用户放行 `/api/v1/disaster-events/**`、`/api/v1/survey/**`、`/api/v1/assessment/**`（或补充对应白名单/权限配置并在注释中说明）。

3. 检查前端代理与 Axios 请求封装：
   - 定位前端 `vite.config.js`（或 `vue.config.js`）、`nginx.conf`（如有）以及 Axios 实例配置（如 `src/utils/request.js`）。
   - 检查 `api/disasterEvent*`、`api/survey/pipeline.js`、`api/assessment/pipeline.js` 发出的 `/api/v1/**` 请求：
     a) 在 `vite.config.js` 的 `server.proxy` 中补充或核对 `/api/v1` 的反向代理规则，确保正确转发到后端端口及对应 `context-path`（避免路径重复拼接或丢失）。

任务二：补齐风暴潮评估对调查基线 `CONFIRMED` 状态的强校验
================================================================================

【问题描述】
业务规范要求“灾情调查第 4 步确认并锁定基线（`CONFIRMED`）后，方可作为风暴潮评估的正式输入”。目前 `StormSurgeAssessmentServiceImpl` 虽读取了 `SurveyBaseline`，但未强校验其状态是否为 `CONFIRMED`。

【请 Cursor 按以下步骤修改】
1. 后端评估入口强校验：
   - 文件：`backend/disaster-survey-module/disaster-survey-evaluate-biz/src/main/java/com/santech/module/biz/assessment/service/impl/StormSurgeAssessmentServiceImpl.java`
   - 在执行【经济损失评估 (`STORM_ECONOMIC_LOSS`)】和【综合评估 (`STORM_COMPREHENSIVE`)】前，校验关联的调查基线：
     a) 若根据 `baselineId` 或 `eventId` 查不到调查基线，抛出明确的 `ServiceException`：`"未找到关联的灾情调查基线，请先完成灾情调查"`。
     b) 若查到的基线 `status` 不等于 `BaselineStatusEnum.CONFIRMED.getCode()`（例如仍为 `DRAFT`），抛出明确的 `ServiceException`：`"当前调查基线尚未确认锁定，请先在灾情调查第4步确认基线后再执行评估"`。
   - 检查 `SeaWindAssessmentServiceImpl.java` 和 `SeaWaveAssessmentServiceImpl.java`：若入参显式传了 `baselineId`，同样校验其存在性及状态合法性；若未传则允许独立执行。

2. 后端已确认基线的不可篡改保护：
   - 文件：`SurveyPipelineServiceImpl.java`、`SurveyBaselineServiceImpl.java`
   - 核对 Step2（受灾范围）、Step3（叠置分析）、Step4（对比核查）写回基线时的逻辑：
     - 如果当前最新基线状态已是 `CONFIRMED`，严禁直接覆盖原记录；应自动新建一条 `DRAFT` 状态且 `version_no + 1` 的新版本基线，或明确拦截提示。

3. 前端状态联动提示：
   - 定位风暴潮评估相关前端页面及 `src/store/disasterWorkflow.js`。
   - 进入风暴潮经济损失/综合评估页时，检查当前事件的 `currentBaseline?.status`：
     - 若不是 `CONFIRMED`，在页面顶部展示醒目提示条（说明基线未确认），并提供一键跳转至【灾情调查 - 第4步】的按钮；同时在接口返回该业务异常时正确弹出后端错误信息。
